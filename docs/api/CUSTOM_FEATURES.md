# Trusted local custom batch features

EQ093 adds `equity_features.custom`: CustomDefinition, CustomInput, CustomRequest, BatchCalculator, CustomRegistration and CustomRegistry. Experimental pair0.0.4a2; built-in discovery/39 equations are unchanged. Implementation is pending final review and delivered artifact acceptance; the PR/issue records current status.

A CustomDefinition wraps existing schema1 FeatureDefinition metadata with an implementation ID/version, a configuration rule, primitive parameter types and actual batch-only capabilities. Its inner FeatureDefinition has all execution flags false: the built-in catalog does not certify caller code. Register by `CustomRegistry("demo").register(definition, calculator)`; registration returns a new immutable registry. Namespaced IDs, duplicates and built-in collisions follow existing Registry rules. `list_features()` and `get(id)` discover explicit custom registrations. Built-in functions remain their existing APIs.

Use one canonical:1 input per declared role and one value output named by the exact custom ID. Canonical schemas/kinds/required fields are checked. Initially logical result/session/evidence input requirements and custom update/restore/merge are unsupported. Canonical inputs are supplied even for empty/missing fields; whole absent-input acquisition is outside this API. Batch calculators receive CustomRequest(inputs, config, entity), with CustomInput(role, batch) values. ConfigSpec identity equals custom ID, algorithm version equals definition, and parameter names/exact primitive types equal the declared schema. Configuration rule and semantic value restrictions belong to the calculator.

`registry.compute(id, request)` invokes the explicit callable only after mode/request admission. Return a FeatureResult with exactly one column, one requested entity, matching custom ID/algorithm/schema/dtype/unit/nullability. Use `request.metadata(definition)` for exact config digest, C/K/E, canonical role/source metadata and implementation backend ID/version. Initial evidence retention is zero. Returned owned result components are recursively reconstructed through their public constructors, including structured cells, quality/entity and metadata/input components. Expected request metadata is copied before invocation to reject shared-binding mutation. Existing quality/null/finite-value and evidence admission applies. Changed identity/schema/version/units/config/input/implementation bindings reject with typed ContractError. Unknown IDs, unsupported modes and malformed requests reject before invocation. Callback exceptions propagate unchanged; the library does not disguise caller errors as numerical success.

Metadata `CustomDefinition.to_json()` contains no callable. It supports inspection only; there is no executable from_json, plugin loading, expression evaluation, pickle, upload, source discovery or remote API. CustomRegistry and callbacks are never serialized by this API. Different equations use different namespaced IDs/algorithm versions; supported built-in parameters do not rename built-in mathematics.

## Independent synthetic consumer

`examples/external_consumer` is a separately built/installable equity-feature-demo distribution using public imports. Build/install the two core artifacts, then build its wheel with pinned build tools and install using `--no-index --no-deps`. Run `python -I -c "from equity_feature_demo import main; main()"` outside the source tree. `tools/build_foundation.py` performs this for each fresh wheel/sdist pair and runs extension negatives in that environment.

The example supplies O100/H103/L99/C102 and O102/H104/L101/C103. Session O100/H104/L99/C103 yields custom demo:range_over_open/v2 = (104-99)/100 = 0.05 fraction; built-in session.price.range_fraction/v1 = (104-99)/103 = 5/103. The calculator uses public admitted built-in OHLC with its explicit v1 operand configuration and binds its own v2 config/implementation to the result. Missing/incomplete/future/unknown operands propagate unavailable quality; zero open is not_applicable/zero_denominator (positive-price admission normally prevents that branch).

Callables are trusted local Python. Contract conformance does not prove equation correctness, source truth, temporal policy implementation, determinism, purity, sandboxing or resource limits. The example independently tests its equation and relies on already-qualified built-in temporal admission for operands. Hosted interfaces require separately approved server implementations and never accept client executable uploads. EQ039/040/044/095 and final R3 acceptance qualify broader documentation, compatibility and installed consumer integration.
