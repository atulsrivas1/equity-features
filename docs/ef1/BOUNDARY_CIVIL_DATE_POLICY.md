# Civil-date static boundary policy

The pure feature packages use supplied civil Gregorian dates for period boundaries and daily observations. Constructing `date(year, month, day)`, parsing a supplied ISO date, and adding a supplied `timedelta` do not require the current date, a timezone lookup or provider access. The outer provenance preflight also parses supplied session strings. This checker correction changes no calculation, contract, package version or numerical fixture.

The static checker admits only absolute `from datetime import date` and/or `timedelta`, including import aliases. It keeps the `datetime` namespace, clock/time/timezone classes and all other imported members closed. Imported classes may appear in type annotations, direct constructor calls, and direct `date.fromisoformat(...)` calls. Assignment aliases, class/callable arguments, returned classes, containers and extracted methods accessed through the imported class binding are refused; ordinary returned date values and arithmetic remain allowed. Distinct classes cannot share a local import name; identical repeated imports remain unambiguous. A caller can use `from datetime import date as CivilDate` instead of assigning the class to another name.

The same civil-date helper applies to the pure and outer provenance profiles. It rejects selected current-clock/local-time conversion and locale-sensitive formatting attributes, including those accessed through date instances or helper returns. It also rejects reflective date-class escape in a module importing these classes and ambiguous imported-class rebinding. The existing reviewed `pyarrow.timestamp` constructor remains admitted through its exact resolved backend identity, including the previously supported namespace aliases and extracted callable aliases; an arbitrary object's `.timestamp` and ambiguous backend rebinding are refused. Existing generic reflection, file, network and backend restrictions remain. Other package profiles receive no new date import permission.

This is advisory AST policy checking, not a Python sandbox or a complete type/data-flow proof. The checker does not execute date parsing or validate constructor argument values. Its class-extraction rule follows imported class bindings, not complete flow/types of constructed instances. For example, `d=CivilDate(2026,1,1); parse=d.fromisoformat` is admitted, while extracting `CivilDate.fromisoformat` through the imported class binding is refused. Selected ambient attribute names such as `d.today` remain refused on any receiver. Date-value methods such as `weekday`, `replace` and `isoformat`, civil fields and arithmetic remain deterministic for the supplied inputs. The tool does not claim to whitelist every possible operation on every runtime object; denied-entrypoint execution audits remain separate evidence.

Two further existing false refusals use equally narrow exceptions. Direct `re.compile(...)` is admitted only through a proven `import re` namespace, including import aliases, without ambiguous namespace rebinding or escape. Extracted callables, Python's built-in `compile`, arbitrary `.compile`, shadowed namespaces and reflective namespace mutation remain refused. A local name `time` is admitted only for structurally declared event/effective-time column scalars used directly in comparisons: a column subscript assignment, a comprehension target, or the second target of an enumerated column loop. Callable/attribute use, aliases, function arguments, imports and ambiguous rebinding remain refused; neither the `time` module nor an arbitrary `.time` gains permission. This rule checks source shape, not runtime element types or arbitrary caller behavior.

The reviewed predecessor's Windows development checks passed its existing policy fixtures, but independent edge probes exposed namespace/callable timestamp alias regressions and conflicting civil import aliases. Those prior results remain historical. The corrected candidate adds timestamp compatibility and ambiguity fixtures, rejects conflicting civil classes, and states the instance-flow limitation explicitly. Final byte identities and actual successor checks are recorded separately; no predecessor result is relabelled as validation of changed source.

Actual final `python -B tools/check_boundary.py` passes all package scans, new policy controls, and existing intraday/continuous/core/research/outer/conformance/agent/ledger checks. Retained failed attempts exposed the separate regex and scalar-name false refusals before their explicitly scoped corrections. A civil rebinding control also exposed an initial walrus guard omission; the final checker refuses it. These development results concern this checker source only. No numerical rerun, installed/platform qualification or release acceptance is claimed. Earlier frozen cohort full-boundary failures remain historical evidence and are not relabelled by this checker correction.
