# EF4 tape implementation

[EQ-158 #492](https://github.com/atulsrivas1/equity-features/issues/492) and [EQ-162 #496](https://github.com/atulsrivas1/equity-features/issues/496) library layer: the pure `ef4.tape_window_sign` (nine `tape.window.*` and `tape.tick.*` outputs) and `ef4.trade_top_k_notional` (`tape.top_k_notional`) producers in `packages/features` (module `equity_features.ef4`, next to `ef3`). The frozen [contract](TAPE_CONTRACT_PROPOSAL.md) (versions `ef4-tape1` and `ef4-notional1`, decisions DP-T*, DP-K*, DP-Q1, DP-R1, DP-P1, DP-M1, DP-H1 and rulings OQ-1 to OQ-10) governs; this slice implements it and redefines nothing. The EF4 I/O mapping, worker and release acceptance (EQ-163) layers remain separate.

## Structure

`packages/features/src/equity_features/ef4/`: `_tape_common` (the accepted trade admission, per-row knowledge flags, capability helper), `_tape_window` (config, seed admission, tick chain, totals, readiness, evidence), `_tape_topk` (config, notional rank, partition merge, readiness, evidence), `_tape_definitions` (own discovery and capability check, its own module) and `_tape_dispatch` (`compute_ef4_tape`, routed by config identity). It reuses the EF3 admission helpers (`parameter_map`, `check_policy`, `check_features`, `check_slots`, `check_entity`, `make_config`, `first_status`, `ordered`, `_check_meta`, `check_reference_id`) and `to_float`, and the accepted `session.trade` admission (`_admit_trades`); none of these is changed. The EF4 package registers nothing in the core registry: `describe_intraday()` and its catalog digest, the core session registry, the shared validators, every EF1/EF2/EF3 output, the size-ranked `session.trade.top_k` and every published R17 result are unchanged, and no package version is bumped.

## Public surface

Window producer: `build_tape_window_config`, `decode_tape_window_config`, `compute_tape_window` (role slots `(trades, seed)`), `TAPE_FEATURES`. Notional top-K: `build_notional_top_k_config`, `decode_notional_top_k_config`, `compute_trade_top_k_notional` (role slot `(trades,)`), `merge_trade_top_k_notional`, `NotionalPartial`, `notional_key`, `notional_cell`. Closed dispatch `compute_ef4_tape`, discovery `ef4_tape_definitions` and `require_ef4_tape_capability` (window: batch only; top-K: batch and merge, update and restore unsupported). Every builder parameter is keyword only and has no default (`policy_version`, `window_ns`, `seed_policy`, `top_k`, `evidence_limit`, `eligibility_policy`); the session must keep opening and closing auction inclusion false for the window producer (`INVALID_CONFIG` otherwise). Entity, session, instrument, seed reference id and role bindings come from `EntityKey`, `ConfigSpec`, the bound batches and their fact rows; no identity is a constant of the library.

## Mathematics and numeric policy

Everything runs on exact Python integers: one pass over the supplied order computes the tick sign chain (the seed is the first reference; an unchanged price carries the previous sign; ineligible prints are skipped) and, for the prints at or after `C - W`, the count, volume, price times size sums and the signed splits. A selected output checks only its own value (`checked_int64` for the volume sums and splits, `checked_decimal128` for the two notional coefficients; `OVERFLOW` is a typed failure, never a wrap), so an output that is already unavailable never forms its sum. Imbalance is one correctly rounded `Fraction` to float64 (`+0.0` when the net volume is zero), `zero_denominator` when the window volume is zero. The notional top-K ranks on `(-price * size, event_ns, order_key, event_id)` with a bisect insertion that retains at most K + 1 candidates.

## Readiness, counts and evidence

Readiness follows DP-T12 exactly: a window output needs the in-window rows (and the size and price columns it uses), a sign-based output the rows from the open to C, both columns and, when the policy is `supplied`, the seed. Undelivered columns are `absent_input` statically (also with no eligible row); the top-K needs a column only when an eligible row exists. Counts: `expected` is the declared coverage count (plus the seed slot for sign-based outputs when supplied), `observed` is the delivered rows minus the unready rows of the output's closure, 0 for an absent column and 0 and 0 with no batch. Reasons are all applicable ones in lexical order and the status follows the first in the accepted precedence; `reconstruction` configs raise no knowledge reason (DP-M1). Evidence for available outputs only: the window outputs list `seed:<reference_id>` first (sign-based outputs with a supplied seed) and then `trade:<event_id>` in canonical order, cut to `evidence_limit` with the seed counting toward it; the top-K lists the retained rows in rank order with the boundary `closing_auction` for a print at the cutoff.

## Notes and deviations from the contract text

1. **The shared `TopKTrades` constructor ranks by size.** `TopKTrades.__post_init__` requires the rows in the size-ranked order (`TopKTradeRow.rank_key`), so it refuses a notional-ranked cell (a K = 2 cell of a print with the larger notional but smaller size, first, raises `INVALID_ORDER`), although the contract keeps the cell, its Arrow struct and every shared validator unchanged and TK01 itself ranks `d, a, c` against the size order `e, b, d`. `notional_cell` therefore validates the rows with the shared constructor in the size order (types, bounds, duplicates, K) and assembles the frozen cell in the notional order without the second ordering check. Any later code that rebuilds the cell through the constructor (for example `dataclasses.replace` or a codec that revalidates the order) refuses a notional-ranked cell; a contract amendment is needed (a ranking-aware order check or a ranking field) before the I/O and worker layers rely on the cell. This is the main risk of this slice.
2. **Evidence limit is per output.** DP-T15 bounds each available output by `evidence_limit`, while the shared `FeatureResult` bounds the whole table by `ResultMetadata.evidence_limit`. The window result therefore publishes the fixed bound `evidence_limit * 9` (the number of window outputs, whatever the selection) in `ResultMetadata.evidence_limit`, so it does not depend on the selection and a full selection reproduces every fixture witness list; the config parameter is unchanged.
3. **Top-K evidence row ids are the plain `event_id`.** The shared result validator binds a top-K cell row to its evidence by `row_id == event_id` (as for `session.trade.top_k`); the contract notation `trade:<event_id>` for top-K witnesses is therefore plain `event_id` in the result (the fixtures' `trade:` prefix is notation); `trade:<event_id>` and `seed:<reference_id>` are used for the window outputs only, where the contract states them.
4. **Seed reference ids** use the shared closed `x1:` grammar, `x1:` followed by the URL-safe base64 of the caller's seed-set id (the contract's `x1:B(seed_set_id)`); anything else is `INVALID_SCHEMA`. The seed batch also carries the shared REFERENCE validators, `_check_meta` against the config and `require_compatible_inputs` against the trades.
5. **Merge shape.** The contract defines the merge rule, not the call. `merge_trade_top_k_notional` takes `NotionalPartial(config, entity, result)` items (the config is needed for the refusal order of DP-K6: policy version, price unit, adjustment, eligibility policy, K and evidence limit, then entity, market cutoff and knowledge cutoff, then partial row order, then retained duplicates), checks that each result was computed with its config digest and returns a result whose metadata binds every partial input under the role `p<i>.<role>`; a merged result can itself be a partial of a further merge (associativity, PM04b and PM06). An empty list is `INVALID_CONFIG`.
6. **Capability.** Update, restore and merge of the window producer and update and restore of the top-K are `UNSUPPORTED_CAPABILITY`; the merge of the top-K is the explicit `merge_trade_top_k_notional`, and `require_ef4_tape_capability` reports it as supported for `tape.top_k_notional`.

## Rulings to pin in the EF4 shared amendment

Coordinator decision: no shared-validator change in EF4; a rank-aware `TopKTrades` order check goes into the EF4 shared amendment before I/O readback. Until then the workaround is pinned: `notional_cell` (used by `compute_trade_top_k_notional` and `merge_trade_top_k_notional`) builds the cell with `object.__new__(TopKTrades)` and `object.__setattr__`. Any `dataclasses.replace(cell)`, `TopKTrades(k, rows)` on notional-ordered rows or a state restore that revalidates raises `INVALID_ORDER`. Top-K witnesses are plain `event_id`, window witnesses keep the `trade:` / `seed:` prefixes. Capability is checked before the unknown feature (contract refusal order).

## Author source validation

A standalone manual script (not committed, no test files added) expanded the contract fixtures with the unmodified author harness `ef4g_fixture_expand.py` under its two unrelated identity bindings, built canonical batches, configs and seed facts and ran the library. The author reports 82 of 82 result fixtures (50 window, 25 top-K, 7 partition-merge, 874 + 50 + 14 compared outputs over both bindings), 3 of 3 generated differential fixtures (G01 and G02 window totals for every window, G03 single pass and the index-mod-4 merge for every K) and 75 of 75 refusal recipes matching status, reasons, counts, witnesses, value per acceptance class (exact integer, exact float64, bit exact `+0.0`, tolerance) and error code (author-reported; not independently confirmed here). A deliberately broken tick carry and a size-ranked insertion made the same script fail on the window, top-K, merge and refusal parts, so the comparison is not vacuous. `describe_intraday()` (8 entries) and its catalog digest were identical before and after, and the diff touches no existing source file.

## Cost

20000 prints: all nine window outputs in about 0.12 s and `tape.top_k_notional` with K = 64 in about 0.17 s on one machine (author-observed single runs, not a performance claim or gate). The pass is O(n) with O(1) numeric state; the top-K keeps at most K + 1 candidates and a merge touches P * K rows.

See the [tape window API](../api/EF4_TAPE_WINDOW.md) and the [notional top-K API](../api/EF4_TAPE_TOP_K_NOTIONAL.md). No I/O, worker, installed, cross-layer, performance or release claim follows from this source result.
