## Architecture that stays fixed

Create two planned distributions: `equity-feature-contracts` / `equity_feature_contracts` and `equity-features` / `equity_features`. Use typed Python, with NumPy/PyArrow batch interoperability where justified. Runtime/dependency versions are an EQ-008 decision, not an unverified promise. Calculation functions receive caller-supplied in-memory data; they never fetch, read files/databases, resolve credentials, schedule jobs, publish output or consult the wall clock. Adapter protocols belong in dependency-light contracts; concrete adapters and workers are later releases.

Preserve explicit identity namespaces, UTC nanoseconds, scaled integer prices with scale/currency, integer counts/volumes, overflow-safe accumulation, supplied sessions/calendars and deterministic tie ordering. Missing, empty, zero and invalid are distinct. Availability, adjustment basis, quality, algorithm/config/input identities and evidence must survive calculation. No silent sorting, deduplication, basis conversion, future leakage or invented coverage. Optimize only with correctness parity and measurements. Native acceleration remains a later profiled decision.

## Execution and evidence loop

1. Inspect clean checkout, live issue/Project status and open PRs. Preserve unrelated changes; identify blockers explicitly. Read the next issue and prerequisites, complete its plan and then mark Ready/In progress as supported by evidence.
2. Use a short-lived `codex/` branch and linked draft PR. Update the issue, applicable design/API/decisions/examples and continuity alongside implementation. Keep synthetic or licensed public fixtures. Avoid publishing private paths, datasets or credentials.
3. Run the existing planning check from `.github/workflows/docs.yml` and all three reference verifiers, plus new relevant story-specific tests, typing/build/import checks. Stop on failures. Test meaningful independent expected results, not duplicated implementation. Review the concrete diff and address findings; label self-review honestly.
4. Follow Backlog -> Ready -> In progress -> Code review -> Test -> Ready to release -> Released -> Done with actual evidence. CI must pass on the exact final PR head before merging. Update states and attach created PRs to the execution chat. Do not silently waive missing checks.
5. Verify default-branch publication and relevant post-delivery checks. Documentation delivery can be validated content on main; implementation requires a declared artifact/channel and verification. Merging source alone is not release evidence. Keep implementation Ready to release if its delivery gate remains unmet.
6. Record commands/results, actual review, artifact identity/checksums where applicable, limitations, acceptance, links and resume steps. Close each story only after verified delivery. Update epic checklists/status without falsely closing later-release children.

The R0 internal implementation channel may be versioned foundation wheels/sdists retained as downloadable CI artifacts with checksums and clean-install evidence, established by EQ-009 and recorded consistently in affected stories. Document the artifact retention window and reproducible rebuild path. No public registry publication is authorized.
