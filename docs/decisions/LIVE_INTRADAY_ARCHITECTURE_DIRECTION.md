# Architecture direction: fresh intraday data for traders

Owner decision, October 18, 2026. Prioritize correct, fresh live intraday calculated data delivered quickly to traders; end-of-day work may tolerate delay. Reserve a future release without starting it now. Current architecture and future code should preserve a practical path to this goal.

[GOV029#455](https://github.com/atulsrivas1/equity-features/issues/455) publishes this prospective direction. [Future release](../FUTURE_LIVE_INTRADAY_RELEASE.md) remains deferred. No feed, universe, transport, publication cadence, latency SLA, date or numbered next release is selected. One-second publication was an assistant suggestion and is not an accepted target. This document changes design/review expectations after reviewed publication; it neither implements a live pipeline nor mandates immediate migration of batch features.

## Retain the useful architecture

Keep pure numerical kernels and inward package dependencies. Calculations consume supplied immutable data/configuration/history/reference facts; fetching, files/databases, credentials, wall-clock reads, scheduling and output publication remain outside kernels. The direct local calculation path remains available; optional adapters, workers, services, MCP and evidence consumers must not become prerequisites for local calculations.

The [completed overall audit](../reviews/OVERALL_ARCHITECTURE_REVIEW_2026-10-18.md) found no new actionable correctness defect in inspected paths and supported retaining this architecture. It established parallel capability, not a general end-to-end speedup. Historical throughput timings do not establish live latency. No rewrite or new orchestration framework follows from this direction.

## Prospective design and code-review rules

1. **Declare capabilities.** State batch/update/checkpoint/restore/legal-merge/replay support and limits per feature. Batch-only is a valid explicit disposition. It must not be described as live-ready. An advertised incremental mode needs bounded sufficient state and a declared initialization/history/reference contract, rather than an implicit full-history reload on every event. Document material tradeoffs.
2. **Preserve causality and state ownership.** Keep ordered state local to its instrument/stream where valid. Parallelize independent groups only; respect chronological/history/dependency and universe/breadth barriers and declared legal merges. Caller callbacks and factories are trusted code, not automatically thread-safe or sandboxed. Preserve UTC nanoseconds, scaled prices, cutoffs and known-at availability.
3. **Leave orchestration outside calculations.** Permit persistent orchestration and reusable supplied history/reference state without making a process launch, connection setup or durable write per event an architectural requirement. A material exception needs a documented reason. Do not make every trader update wait for the entire catalog/universe/EOD job unless its mathematics requires that dependency. Keep required validation, receipt, authorization and identity guarantees.
4. **Bound work and expose overload.** A future live path needs bounded queues/state, admission/backpressure, explicit overload/recovery and observable freshness/backlog. Declare worker/native-thread budgets and live/background priorities when implementing that path. Logical limits are not hard physical resource guarantees. This decision changes no current scheduler or worker default.
5. **Declare temporal and recovery semantics.** Carry source/input identity, event/as-of/cutoff and knowledge availability, quality/completeness, provisional/final and revision semantics. Declare duplicates, late/corrected events, gaps and reconnect/replay behavior. Do not silently drop required raw events, claim completeness from missing coverage, forward-fill without contract, or invent watermarks. Outbound snapshot coalescing is permitted only under an explicit delivery contract; it cannot discard events required for calculation.
6. **Measure the actual outcome.** Distinguish bulk throughput from received-event-to-consumer availability and event age/freshness. Report p50/p95/p99 under representative rates/bursts/load with workload, hardware and clock-comparability assumptions. Performance adoption requires full numerical/status/quality/evidence/input-identity parity. Synthetic replay, historical timings and source inspection have different evidence limits. No new timing result or numeric target is asserted here.

Apply the relevant checks to new or changed behavior. Record a no-impact or batch-only disposition where appropriate. Ordinary batch work does not depend on implementing this future release. A change that materially forecloses the live path needs an explicit reviewed tradeoff and, where it changes agreed scope or public commitments, the normal owner decision. No blanket veto on batch features and no automatic requirement to benchmark documentation edits is introduced.

## Current support and remaining work

Current SessionAccumulator support is limited to declared R1 session capabilities; R2/custom incremental support is not implied. Ordered chunks, explicit prefix coverage and replay for unsupported late/corrected inputs remain required. A checkpoint or incremental kernel is not an entitled live feed, reconnect controller or trader delivery service. Existing adapter/provider limitations and current accepted mathematical specifications remain authoritative.

Future selection must freeze a practical feature slice, actual feed rights/account/sequence/schema/coverage, initialization and replay policy, universe/rates/bursts, delivery consumer/transport, numeric latency/freshness/error/backlog budgets and permitted target operations. Qualify correctness, gaps/recovery/overload/EOD contention and both supported platforms before delivery claims. Existing security/research/combined C1/witness/provider backlog is unchanged; reuse selected prerequisites rather than duplicate them.

This is a planning and prospective architecture decision only. No runtime/API/schema/default/dependency change, provider/private/paid acquisition, deployment, account administration, trading, recurring work or physical-guarantee claim is authorized. Existing review and release gates remain mandatory.
